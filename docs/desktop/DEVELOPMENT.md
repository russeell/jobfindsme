阶段交接采用主动回传：实施者保存证据并停止写入后，向当前调度任务发送完成摘要；具体 ID 与消息格式见管理 skill 的 orchestration 引用。heartbeat 仅用于漏报/中断恢复。

D05 的实现依赖已完成的 D04b 检索契约，不依赖全部平台真实登录。D01/D04 的完整来源验收仍保留，并加入 D12 最终发行验收依赖；未验证来源持续禁用，不以离线检查代替实测。

## 1. 单一任务入口

`REFACTOR.md` 管范围，`TECHNICAL.md` 管实现，`tasks.json` 管进度。现有 README/旧架构文档记录旧产品，迁移期间不作为新需求依据。
后续管理 skill 必须读这些文件与根目录 AGENTS.md；不复制另一份功能清单。
开发管理 skill 源文件位于 `.agents/skills/jobfindsme-dev/`；最新版 UI 归档在 `docs/desktop/ui/`。
用户已授权全自动开发：当前会话调度，实施任务使用用户指定的 GPT-6 Astra 低推理，沿用已确认 UI。调度规则见 `ORCHESTRATION.md`。2026-09-21 起允许本地提交，仍禁止自动推送和发布。

任务状态只用 `pending / in_progress / blocked / done`。默认一次推进一个可验收任务；任务太大则拆分，保留依赖关系。
选择规则：按清单顺序，选依赖均已 done 的首个 pending 任务。blocked 任务写清具体原因，不虚报完成；可以继续不依赖它的任务。

D01 只负责四平台真实登录、列表、详情、分页和投递页的最终外部验收；缺少真实账号会话时保持 blocked。D04 的离线前置实现拆为 D04a（隔离浏览器、持久会话、能力状态与门禁）和 D04b（简历检索词、连接器适配、分页预算与官网目录），二者可以在 D01 blocked 时独立完成。D04 仍依赖 D01/D04a/D04b，负责真实来源完整接入验收；不得通过删除验收或把页面可打开当作来源可用来解除阻塞。

## 2. 每轮开发流程

1. 看工作区变更、当前任务及交接，保留用户已有修改；只读必要代码。
2. 写清本轮目标、允许改动范围和最小验收，设置 in_progress。
3. 完成一个端到端小功能；遇到新的范围变化先更新计划，不擅自扩大需求。
4. 运行该任务的针对性验证；修复失败后只复跑受影响项。
5. 在任务 evidence 中记录命令/手工步骤、结果、日期、版本或差异标识、已知限制；全部验收满足才能 done。
6. 更新简短交接：完成了什么、剩余问题、下一个任务。不记录每条工具调用。
7. 每完成一个独立修复且针对性验证通过，提交一次本地 Git 记录，代码与对应证据一起提交。先检查暂存差异，排除密钥、登录数据、私人简历和生成产物；不混入其他任务修改，不重写历史，不自动推送或发布。首次基线记录当前实现及未完成项，不倒造历史提交，也不将基线提交等同于所有来源验收完成。

重构开始时建立 `codex/desktop-refactor` 分支；不重写用户现有提交。开发不设 human review 关卡，正常实现、验证和修复自主完成；发布线上版本单独由用户发起。

## 3. 适量测试策略

| 改动风险 | 必须验证 | 不需要做 |
| --- | --- | --- |
| 文档/文案/纯样式 | 链接或配置格式检查；受影响页面人工查看 | 全量后端测试、新增文案快照 |
| 分页/硬过滤/评分/阅读记录 | 相关单元测试 + 一个跨页或状态边界用例 | 每改一个函数重跑全部测试 |
| 简历解析/补丁/脱敏 | 对应格式或事实样例；原文不覆盖、隐私不外发、补丁版本冲突 | 为每句模型输出写固定字符串断言 |
| 登录/浏览器/导出 | 每个平台或格式一次有记录的人工冒烟；关键错误路径用离线样例 | 持续自动登录、反复真实投递或联网全量回归 |
| 数据迁移/鉴权/调度去重 | 针对性集成测试：备份恢复、旧数据、重复执行、未授权访问 | 用大量同义用例重复覆盖同一分支 |
| 阶段合并/发行 | 核心回归、类型/构建检查、一次桌面主流程；发行时跑保留的完整测试集一次 | 无新改动、无新失败时再次全量运行 |

测试价值以“能拦住哪种真实失败”为准；不设武断的用例数量或覆盖率目标。
优先复用现有样例，外部平台请求默认用录制且脱敏的契约样例；真实验证只在接入变更或发行证据过期时执行。
同一差异已通过的检查不重复运行，除非后续修改影响其结论。既有无关失败单独报告，不趁机重构无关代码。

## 4. 完成与交接

任务完成必须同时满足：功能存在、验收通过、证据可查、没有未注明的阻塞。截图只能证明界面，不证明真实检索或投递成功。
阶段 2 验收走一次：确认简历 → 检索 → 翻页 → 研究入口 → 平台原页 → 手动更新投递记录；没有用户真实投递意图时停在提交之前。
外部来源用“已验证/部分可用/受限/待验证”报告，模拟结果不得算作接入验收。
证据写在 `docs/desktop/evidence/<task-id>.md`，记录结果、复现方式与限制。原始截图、长日志、一次性脚本和临时 JSON 留在本机忽略目录；确需引用的历史附件用不可变 Git 提交链接，不再放入当前 GitHub 文件树。不提交真实简历、会话或密钥。

性能先建立基线：首批结果时间、来源耗时、字段覆盖、重复率、翻页稳定性。根据测量优化，不把“快、全”当无边界承诺。
每次交接最多五项：本轮完成、验证结果、未解决问题、修改文件、下一任务。

## 5. 管理 skill 与独立 AI review

支持“查看进度 / 继续开发 / 验收当前任务 / 记录阻塞 / 更新计划”。交接入口为 `HANDOFF.md`。
skill 每轮读取 `tasks.json`，按依赖选择任务，执行上述流程，并给出简短交接。
只管理开发，不使用真实求职账号执行未授权投递，不擅自发布，不自动创建定时任务。
当前启用用户授权的阶段会话调度，同一代码目录保持单写入者，不以反复测试或生成大量报告代替功能推进。
新增任务必须包含 `id、title、depends_on、scope、acceptance、verification、status、evidence`，沿用当前清单结构。

鉴权、隐私、迁移、跨模块契约和重大集成有必要时在新 session 做独立 AI review；不是每任务必走流程。
先完成具体实现和最小验证，再提供精确差异（包含未提交/未跟踪文件）及验收包给只读审查会话。
主开发者核实发现并修复，只复跑受影响验证；无需用户人工审核。登录/验证码等必要用户操作不属于代码 review。
审查步骤见 skill 的 `references/ai-review.md`。不为追求无建议而反复审查同一差异。
